### 身份模型的两次反转（最重要的上下文）

这是这一轮的核心，也是下一个人最容易看糊涂的地方。**顺序是**：

1. 原本：兑换码带手机号姓名（「绑定码」），或匿名码
2. `013` 改成**码 + 手机号**：她手打手机号，跟名单核对
3. `016` 又改成**码 + 从名单里选自己是哪一位**（园所 → 班级 → 岗位·姓氏），
   并把 `teachers.phone`、`teacher_roster.phone`、`redemption_codes` 的身份列**全部删掉**

**为什么最后落在第 3 版**（用户的判断，我认同）：11 位手打打错一位是常事，
而她分不清是「码坏了」还是「我打错了」；手机号在一个园里本来也不是秘密；
她要证明的事情只是「我是阳光幼儿园小一班的主班」，那句话里没有手机号 ——
**库里少一样可识别到人的东西，就少一整套合规义务**。

**要认下来的代价**（已写进代码注释和 operations.md）：从列表里选是一个**表单字段，不是钥匙**，
谁有码都能滚到任何一行。真正的门槛只剩兑换码那一把。可以接受，因为同事之间冒领没有收益，
而「手滑选错同班另一位」是可查可改的（`claimed_openid` 记着是谁认领的）。
**这件事一定会发生，别当异常。**

**三层身份，别混**（`teacher_ref` / 名单行 id / `teachers.id`）—— 见 `CLAUDE.md`。
追人按 `teacher_ref` 归组，追班按（园所 + 班级）归组。

## 这一轮真踩过的坑（不是预防性提醒）

### 1. `dev:` 假登录会把中文从 openid 里剥掉

`services/wechat.js` 里 `replace(/[^a-zA-Z0-9_-]/g, '')`。
我在 `tasks-test.mjs` 里用中文当 tag 造了「五位老师」，**全部塌成同一个 openid** ——
测出来的结果看着随机，查了一阵。
现在名字用中文（可读）、openid 用 ASCII slug，并且加了一条断言盯着
「她们真是五个不同的账号」。**写涉及多账号的脚本时先看那条断言。**

### 2. 回归断言里的绝对数字会随轮次变红

两次栽在同一件事上：
- `tasks-test` 用真省市名（广东/浙江）定向 → 命中上几轮留下的园 → 「试算说 2 位」永远对不上
- 上一轮 `roles-test` 假设「每位老师都有手机号」→ 匿名码之后那是合法空值

**判据**：断言要么验不变量（「活跃 ≤ 总数」），要么把测试数据做成本轮独有（省市带 RND）。
一个会随机变红的断言，**红两次之后整份脚本就没人看了** ——
这一轮也因此把 `test:api` 里一条会随机红的断言（「换年龄班后字母指向的文案一定变了」，
而选项是模型生成的）改成了打一行观察。

### 3. `test:mp` 那条 handler key 检查是真有用的

改完「我的」页之后它抓到 `goRedeem` 和 `onSuggestionInput` 都是 `8e`。
按 `CLAUDE.md` 那条改名（`goRedeem` → `onRedeemTap`）解决。
**别当误报放过去。** 注意 key 不只跟 handler 名有关，加了新 handler 之后旧的也可能变。

### 4. 改数据模型之后要回头看协议页

`016` 删掉手机号之后，协议里三句话（「你填问卷时留的手机号」等）当场变成假话。
**不实的隐私说明比没有更糟。** 这已经是协议文案第二次因为数据模型变动而改
（第一次是加同事账号，「只有开发者本人」不再准确）。
`operations.md` 第 2 节记了这条纪律。

### 5. cleanup 脚本会跟着模型变动一起坏

`016` 删列之后它一跑就崩（还在查 `teachers.phone`）。
顺带补了两处它自己造成的不一致：
- 删假账号之后名单那一行的 `claimed_by` 被外键置空、status 还是 claimed →
  那个位置永远占着还看不出为什么。现在放回 pending
- 回归脚本自建的园和任务跑十轮攒十个 → 按脚本的命名规律删

### 6. 换绑做完之后才发现旧设备还能用

换绑是把 openid 挪到**旧那一行**上，所以旧 token 指向的行还在、status 还是 active，
`requireAuth` 拦不住它 —— 而换绑的常见起因就是手机丢了。
`015` 加了 `token_version`，换绑时 +1。
**注销没有这个问题**（它把 status 改成 deleted，`requireAuth` 那道立刻生效）。

### 7. chrome-devtools 的截图在这个环境里不稳

多次 120 秒超时。有一次是**页面上挂着一个没关掉的 `confirm` 对话框**（用
`handle_dialog` 关掉即可），另几次原因不明。
**改用 `evaluate_script` 读 DOM 文本**，这一路都可靠，而且比截图更适合断言。

## 与用户协作的注意事项

- 用户是产品负责人，不是专业开发者。**说清楚「为什么」比「怎么做」重要**，
  他要求过「用更朴素的话说」，少用术语
- 他对**界面上的解释性文字零容忍**。这条已经写进 `CLAUDE.md`（含判断标准：
  「她不看这句话会做错什么吗？」答不出来就删）。**写界面前先读那一条**
- 他会**主动提产品级改动**，而且**会推翻自己上一个决定**（这一轮身份模型反转两次）。
  遇到反转不要急着实现 —— 先把新方案的代价说清楚，他接受了再动
- **他在微信开发者工具里看效果，你看不到**。每次交付都要如实说「好不好看得你自己看」
- 他给的方案往往可行但有一处结构性问题（这一轮：想把码绑到手机号上，
  那会让问卷星自动发码断掉）。**接方案 + 指出那一处**，比全盘否定或全盘照做都好
