# 运营体系：身份、额度与反馈

> 2026-08-17 与用户逐项确认后固化。本文件是运营侧的**唯一事实来源**：谁能用、用多少、怎么发、记录什么、谁看得到。
> 状态：**已全部实现**（2026-08-17）。回归脚本 `scripts/ops-test.mjs` 与 `scripts/admin-test.mjs`，都能反复跑。

## 0. 一句话模型

这不是公开产品。老师是合作园的研究参与者：**完成问卷等任务 → 获得使用额度**。
没有任务就没有额度，没有兑换码就进不来。所有额度由开发者手动发放，不存在自动发放。

## 1. 身份：兑换码把问卷和微信账号绑在一起

### 为什么不用微信手机号接口

「手机号快速验证组件」只对企业等非个人主体小程序开放且按次收费。本项目是个人主体，走不通，也不需要走——手机号本来就在问卷里。

### 身份模型

| 层 | 键 | 来源 |
|---|---|---|
| 技术唯一键 | `openid` | 微信登录 |
| 业务身份锚点 | 手机号 | 问卷星（老师自己填的） |
| 连接两者 | **一次性兑换码** | 开发者在后台生成 |

流程：

```
老师填问卷（含手机号）→ 开发者审核 → 后台生成兑换码（预填：手机号/姓名/园所/班级/岗位/初始额度）
→ 微信把码发给老师 → 老师打开小程序，首次登录见「待激活」页 → 输码
→ openid ↔ 手机号绑定完成，额度同步到账
```

- **兑换码是额度唯一的入口**（2026-08-18 反转旧规则）。原来的规则是「码只用于首次激活，
  之后按手机号找到人直接加额度」——后台那个「发额度」按钮已经撤掉了。
  现在**每一笔额度都是一个码**：首次激活是一个码，完成新任务再发一个码，她自己兑。
  为什么这么改：发额度要先在几十个老师里找到她（匿名码激活的老师根本没有手机号可搜），
  而发一个码是无状态的——我不需要知道她是谁，谁拿到谁能兑
- 没有码的人打开小程序：停在待激活页，说明这是合作园项目、如何参与。**这就是权限门槛**
- 一个码只能兑一次，兑过即废；未兑的码可作废
- **已经激活的老师再兑一个码 = 只加额度、身份不动**（`POST /auth/redeem` 管两件事）

## 2. 记录什么、谁看得到

### 记录的字段

| 字段 | 来源 | 说明 |
|---|---|---|
| 手机号 | 问卷 | 业务锚点。后台列表**默认打码**（139\*\*\*\*1234），详情页看全号 |
| 姓名 | 问卷 | 后台需要知道「中二班的哪位老师」才能把积分发对人（用户 2026-08-17 明确要求一并记录） |
| 幼儿园 | 问卷 | 后台维护**固定园所列表**，兑换码生成时从列表选，防止"阳光幼儿园/阳光园"写成两个 |
| 班级 | 问卷 | 如「中二班」。年龄班另有字段（已有） |
| 岗位 | 问卷 | 主班 / 配班 / 保育员 / 园长 / 其他 |
| 对话与成稿 | 使用中产生 | messages / lesson_plans / lesson_images，已在存 |
| 用量 | 派生 | 不建计数器，直接从事实表 count（计数器会和事实漂移） |

### 三条铁律

1. **手机号和姓名永不下发到小程序前端、永不进模型提示词、永不进日志**。它们只活在服务端和管理后台
2. **幼儿园管理者（园长、园方任何人）看不到任何老师的数据**。管理后台只有一个账号——开发者本人。园长即使自己也是用户，看到的也只有她自己的东西。这条要在协议和界面上**加粗明示**，因为老师最大的顾虑不是"开发者看到我"，而是"园长看到我写教案偷懒/写得差"——这个顾虑不卸掉，没人敢真用
3. **不存幼儿的任何信息**——这条红线不变，任何时候不动

### 协议（首次登录，激活前必须同意）

要点，全部大白话：

- 采集范围：手机号、姓名、园所、班级、岗位（来自你填的问卷）；你在小程序里的对话、生成的教案与配图、使用量
- 用途：确认身份、发放额度、研究与产品改进
- **「你的幼儿园和园长看不到这里的任何东西。你的使用记录、写了什么、用了多少次，只有这个项目的团队看得到，不会提供给园方。」**（加粗，原话级别的直白）
  - 2026-08-17 从「只有开发者本人」改成「只有这个项目的团队」：后台加了同事账号之后，
    原来那句话就不准确了。**挂着不准确的隐私承诺，和挂着假承诺是一回事。**
    团队里的一般管理员看不到对话正文和手机号全号（见第 6 节）
- 不收集孩子的任何信息
- 输入和 AI 输出会经过微信内容安全检查（平台要求）

设置页「隐私」区同步重写——现在那句"不存你的手机号和真实姓名"在新模式下是假的，**挂着假隐私承诺比不写更糟**，必须换成上面的诚实版本。

## 3. 额度：只追加、不修改的台账

### 模型

```
余额 = Σ(发放) − 消耗

发放：quota_grants 表，一行一笔，只插入不修改
      (teacher_id, 文案±N, 配图±N, 原因, 发放时间)
      原因必填："完成8月问卷" / "首次激活" / "反馈奖励" / …

消耗：不记账，从事实表派生 ——
      文案 = count(lesson_plans) + Σ max(0, version − 3)
      配图 = count(lesson_images WHERE status='ready')
```

### 消耗规则（已拍板）

| 动作 | 消耗 |
|---|---|
| 生成一份教案 | 文案 1 次 |
| 改稿第 1、2 次（同一份教案） | **免费** |
| 改稿第 3 次起 | 每次文案 1 次 |
| 生成失败 / 改稿失败 | 不消耗（只数成功的） |
| 配图成功 | 配图 1 张 |
| 配图失败 | 不消耗 |

改稿计费不需要新字段：`lesson_plans.version` 本来就随改稿 +1（初稿 v1，两次免费改到 v3），
**version ≥ 4 的那次开始计费**，公式即 `max(0, version − 3)`。

### 闸门位置

- **开新会话**时查文案余额 ≥ 1。不能等到生成时才拦——让老师答完 4 题再告诉她"额度不够"是恶劣的体验
- **改稿**时若 version 已 ≥ 3（下一版将计费），查余额 ≥ 1
- **配图**时查配图余额 ≥ 1（每日 10 张的防刷上限保留，作为第二道闸）
- 余额不足的提示语自带出路：「本月额度用完了——完成问卷任务可以获得更多，联系发你兑换码的那位」

### 「我的」页展示

剩余文案 N 次 · 配图 N 张，点开看台账明细（哪天、哪个任务、加了多少）。老师能对账，就不会觉得额度是黑箱。

## 4. 反馈：两层，都进后台

| 层 | 位置 | 形式 | 绑定 |
|---|---|---|---|
| 教案评价 | 成稿页正文末尾 | 一次点击：直接能用 / 改改能用 / 用不了 + 可选一句话 | lesson_plan_id + version |
| 产品建议 | 「我的」页「提个建议」 | 类型（质量/新功能/别扭/其他）+ 正文 | 无 |

- 教案评价绑定版本，后台看到的是「这份大班搭高塔的 v2 被标了用不了」而不是孤零零一句抱怨——这正是「教案是否真的适龄可用」这个最大未知数的持续数据源
- 反馈文本过 msgSecCheck（UGC 规矩不变）
- 反馈可以作为任务：「提 N 条有效反馈 → 奖励额度」，开发者在后台人工认定有效后手动发（防刷）

## 5. 问卷星操作手册

### 5.1 问卷必备字段（每期问卷都要有这组）

| 字段 | 要求 |
|---|---|
| 手机号 | **必填**，开启问卷星的手机号格式校验。这是对账的唯一锚点 |
| 姓名 | 必填 |
| 幼儿园 | **下拉单选**，选项与后台园所列表一字不差。不要用填空 |
| 班级 | 填空，如「中二班」 |
| 年龄班 | 单选：小班 / 中班 / 大班 |
| 岗位 | 单选：主班 / 配班 / 保育员 / 园长 / 其他 |

研究题项随每期主题变，上面这组身份题**每期固定放最前面**。

### 5.2 新老师首次接入

1. 问卷星后台导出本期答卷
2. 逐条核对：手机号在管理后台**搜不到** → 是新老师
3. 后台「兑换码管理」→ 新建：录入手机号/姓名/园所（下拉选）/班级/岗位 + 初始额度（如文案 20 + 配图 10），原因写「完成〈X月问卷〉·首次」
4. 生成的码通过微信私发给这位老师
5. 老师激活后，后台该码状态变为已使用，账号出现在老师列表

### 5.3 老老师完成新任务

2026-08-18 改了：**不再「进她的账号页加一笔」，而是再发一个码**。

1. 后台「任务」页发起任务（问卷链接 + 奖励额度 + 截止日期 + 定向），
   老师在小程序首页看到条带
2. 她填问卷 → 我导出答卷核对
3. 后台「批量建码」要 N 个（初始额度就是任务承诺的那个数），
   建完弹框里一行一个列出来，复制或下载 CSV
4. 把码发给完成了的那几位，她在「我的」页点「兑换」输进去

为什么绕这一圈而不是直接加：**匿名码激活的老师在后台没有手机号可搜**，
「找到她」这一步本身就不成立。发码是无状态的——我不需要知道她是谁。
代价是多一次转发动作，换来的是整个流程不依赖「我能认出她」。

### 5.4 纪律

- **每一笔额度必须写原因**，这是研究记录也是对账依据
- 问卷星每期导出的 Excel 存档（本地即可），出争议时是原始凭证
- 码未被兑换超过 30 天 → 微信上提醒一次；老师说不用了 → 作废该码

## 6. 管理后台

打开 `http://<域名或 localhost:3000>/admin`。首次启动时系统会用 `.env` 的 `ADMIN_PASSWORD`
自动建一个 `admin` 超级管理员；之后改密码在后台改，那个环境变量就不再起作用。

**当前本地开发密码：`admin` / `123456`**（2026-08-17 用户指定）。
线上部署前必须改掉——后台能看到全部老师的手机号和对话内容，弱密码在公网上等于没有密码。
生产环境启动时若密码短于 12 位，会打印一条醒目的告警。

### 两级权限

2026-08-17 从「只有一个账号」改成多账号，因为同事要帮忙做运营。
这直接触及对老师的承诺，所以权限是这样切的：

| | 超级管理员 | 一般管理员 |
|---|---|---|
| 发额度、建兑换码、园所、反馈 | ✓ | ✓ |
| 老师列表、余额、用量统计 | ✓ | ✓ |
| **手机号全号** | ✓ | ✗ 只看打码 |
| **对话正文与教案内容** | ✓ | ✗ 只看写了几份 |
| **管理员账号管理、操作记录** | ✓ | ✗ |
| 改自己的密码 | ✓ | ✓ |

**为什么这么切**：老师同意的协议里写着「你的幼儿园和园长看不到这里的任何东西」。
同事不是园方，这句承诺依然成立——但原来的措辞「只有开发者**本人**可见」在有第二个人
登录之后就不准确了，所以协议文案同步改成了「项目团队」。

同时把最敏感的两项锁在超管手里：同事做运营根本不需要读老师写了什么。
**每多一个人能读老师写的东西，那句承诺就少一分是真的。**

仍然**没有**「园所管理员」这种角色。要是哪天加了园长只读账号，那句承诺就作废了，
必须先跟老师们重新讲清楚。

### 账号保护

- 不能停用自己（停完就登不进来，得手动改库才能救）
- 最后一个活跃的超级管理员不能被停用
- 密码 scrypt 加盐存储，不存明文
- 登录时用户名不存在也会跑一次哈希比较，防止靠响应时间枚举用户名

### 操作审计

`admin_logs` 表记录发额度、建码、作废、建管理员、改状态等操作。
单人时期这张表没必要（「谁发的」答案永远是「我」），多人之后它是对账的前提——
额度对不上时要能查出是谁在什么时候发的。**审计里不放对话正文，只放操作参数。**

### 页面顺序（2026-08-18 调过）

**园所排在老师前面**，紧跟概览：合作是按园谈的，老师是园带进来的。
原来的顺序（概览 → 老师 → 兑换码 → 园所）反映的是「一个个老师」的视角，
而实际要管的是「哪个园在用、我的钱剩多少、该给谁派任务」。

1. **概览**——① 我的钱（充了/花了/剩多少）② 谁在用（几个园几位老师）
   ③ 哪个园用了多少额度 ④ 等我处理。**删掉了「最近写的」和累计数**
2. **园所**——**特征为主**（省市 / 城乡 / 公办民办 / 教师·幼儿人数 / 联系人），
   用量汇总和编辑收进详情弹窗。特征同时是**任务定向的依据**
3. **老师**——按手机号/姓名/**兑换码**搜、详情、停用。**没有发额度**
4. **兑换码**——单个生成、批量建码（建完弹框里一行一个 + 复制 + 下载 CSV）、作废
5. **反馈**——两个 tab：关于产品 / 关于教案质量
6. **任务**——发起活动通知：问卷链接、奖励额度、截止日期、定向（含发布前试算覆盖人数）
7. **配图模型**（超管）——加/改/删、试画一张、设为默认
8. **管理员**（超管）——建号、重置密码、停用
9. **操作记录**（超管）——带筛选（按人/按动作/按日期）+ 每页 100 条翻页

**老师详情页要回答四件事**（缺哪一件都得跳出去查别的页）：

| 问 | 铺的是什么 | 为什么非要有 |
|---|---|---|
| 她是谁 | 手机号、**她兑的那个码**、园所班级岗位 | 匿名码激活的老师没有手机号也没有姓名，**认她只能靠码** —— 不铺出来这批人在后台就是一行无名氏 |
| 额度用到哪了 | 剩余/已发/已用 + 台账 | **没有发放表单了**（2026-08-18）：额度只走兑换码一条路 |
| 用得怎么样 | 写完几份（只列完成的）、每份出到第几版、画了几张、花了多少 | 配图是成本的主要变量，按人看只有这一处 |
| 她说了什么 | 评价与建议，**点标题直接翻出那一份的正文** | 「大班搭高塔 v2 被标了用不了」，得能立刻看到原文为什么 |

**只列写完的教案**：答题中的草稿不进这张表——那是她被打断留下的半截，
不是「她写过的教案」。库里那些 draft 一行都不动（断点续写依赖它们），只是这个视图不显示。

**「看正文」（超管）**：`GET /plans/:id` 这个接口一直有，但界面上没有入口，等于没有。
现在教案那张表每行一个按钮，弹出教案全文 + 模型自检 + 对话记录。
**能按版本切换**（v1 / v2 / v3 各自的原文和当时那句改稿意见），
对话记录**以 JSON 呈现**，可整块选中复制拿去做研究分析。
这是回答「AI 写的教案到底适不适龄」——这个产品最大的未知数——唯一的办法。

**园所页的重心是特征，不是用量。** 特征不只是档案，它是**任务定向的依据**：
「只发给农村园」「只发给广东的公办园」这些条件全部落在省市 / 城乡 / 办园性质这几个字段上。
用量汇总（老师数、7 天在用、没兑的码、教案数、额度、配图、花费）收进详情弹窗——
一张表塞 15 列谁都读不下来。
点「看老师」跳老师页并预设园所筛选，**不为「这个园的老师列表」再做一份界面**。

`contact_phone` 是园长的号，**一般管理员只看打码**，跟老师手机号同一条纪律。
**有联系人不等于给园方开账号**：仍然没有「园所管理员」这种角色，
那句「你的幼儿园和园长看不到这里的任何东西」依然成立。

## 6.5 任务：告诉老师现在有什么可以换额度

额度只走兑换码之后，缺了一环：**她怎么知道现在有个问卷填了能拿 20 次教案**。
以前只能在微信群里喊一声，谁看到谁没看到我这边一无所知。

任务**不自动发额度**。它只说三件事：做什么（问卷链接）、给多少、什么时候截止。
她填完，我在问卷星那边核对，然后建码发给她。
**系统不去猜「她是不是真填了」**——答卷在问卷星，我们库里没有。

**定向**（这是用户明确要的）：向特定地区或特殊群体发。六个维度可叠加——
省份、城市、城乡、办园性质、具体园所、老师年龄班。
空的那一维不限，非空维度之间是「都要命中」。

发布前有个**试算覆盖人数**。这不是锦上添花：条件叠到六层之后不试算没法确认筛对了，
而发错是发给真人的。匹配逻辑只写一次（`services/tasks.js`），
试算和老师端列表共用同一个函数——写两份迟早分叉，
分叉的表现是「后台说发给 12 个人，实际只有 8 个人看到」。

**没有园所的老师**（匿名码激活、没填园所）只匹配「园所相关维度全空」的任务。
这条要记住：否则她永远收不到任何定向任务，而我们不会知道。

老师端入口：**首页一条条带**（有未读才出现，没有就不占地方）+「我的」页一块。
不新增 tabbar——信息架构是定死的（首页只是一个对话框）。

## 6.6 平台自己的账

概览要回答「我账面上还剩多少钱」，而这个数以前算不出来，因为两头都缺：

- **收**：没有任何充值记录。我在 DeepSeek / 12ai 充了多少，库里一无所知
- **支**：只有配图成本。**文本成本一分钱都没记**——每次调用的 token 数只进了日志，
  而生成一份教案是最贵的那次调用，漏掉它这个数就是错的

所以 011 迁移建了两张表：`platform_topups`（我手录充值）和 `model_calls`（每次文本调用一行）。

```
账面剩余 = Σ充值 − (Σ配图成本 + Σ文本成本)
```

跟额度台账同一个纪律：**余额是算出来的，不是存出来的**。记错了记一笔负数冲账，不改历史。
单价放 `config.js`，按各家官网当时的价填；`model_calls.cost_cents` 落库时就算好，
**不留到查询时再乘**——单价会变，否则改一个常量会让全部历史悄悄漂移。

**成本数据不完整这件事要在界面上说出来**：早期 12 张图没有成本记录、
文本成本是 2026-08-18 之后才开始记的。不说的话那个「花了多少」会被当成全部历史。
