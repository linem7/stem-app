# ADR 001: 技术栈选择

## 状态
已采纳 (2026-08-16)

## 背景

STEM 教案生成 APP 平台需要确定前后端技术栈、模型接入方案、知识库实现方式。

## 决策

### 客户端：微信小程序 + uni-app

**决定**：使用 uni-app 框架开发微信小程序为首要目标，同时保持向 H5 网页/原生 APP 扩展的可能性。

**理由**：
1. 大陆用户获客成本低，微信生态传播力强
2. 无需应用商店上架（个人主体无法上 iOS），缩短上线周期
3. 微信小程序有天然的 HTTPS 强制、域名备案约束，合规风险明确
4. uni-app 一套代码可产多端，未来若要 H5/原生 APP 版本改造成本低
5. 微信提供服务端授权机制，用户隐私保护有标准流程

**取舍**：损失原生性能，但对教案编辑场景无关键影响；需要通过 ICP 备案和微信审核。

---

### 后端：Node.js + Express + 原生 JavaScript（ESM）

**决定**（2026-08-16 敲定，原为"待定"）：Node.js 20 LTS + Express 4 + 原生 JavaScript（ESM 模块），数据库 PostgreSQL，直接用 `pg` 驱动 + SQL，不上 ORM。

**理由**：
1. **与前端同语言**。用户是带着 AI 独立开发，前端 uni-app 是 JavaScript，后端同语言可大幅降低上下文切换成本
2. **不用 TypeScript**：TS 需要额外的编译步骤，会让部署链路多一环，对非专业开发者是净负担。类型安全的收益由 AI 辅助 + 接口文档约束替代
3. **不上 ORM（Prisma/Sequelize）**：教案这个业务的查询很简单（按 teacher_id 查列表、按 id 查详情），ORM 带来的迁移工具链和抽象层收益不抵学习成本。直接写 SQL 更透明，出问题时 AI 也更容易帮忙定位
4. DeepSeek 的 API 是 OpenAI 兼容格式，官方 `openai` npm 包直接换 `baseURL` 即可用
5. 部署轻量：一台 2 核 4G 轻量服务器 + PM2 即可，无需容器编排

**取舍**：放弃了 Python 生态在数据分析上的优势。若日后要做教学质量的统计分析，那部分可以单独用 Python 脚本离线跑，不必绑定主服务的语言。

**明确不做的**：不上 Docker/K8s、不上微服务、不上消息队列。单进程 + 数据库 + 对象存储足够支撑到几千用户，过早的架构复杂度是这个阶段最大的风险。异步任务（教案生成、配图）用进程内队列 + 数据库状态表实现即可。

---

### 文本生成模型：DeepSeek

**决定**：使用 DeepSeek API（深度求索开放平台，platform.deepseek.com）。

**理由**：
1. 已备案国产模型，商用无障碍
2. 费用低（教案生成一次 1–5 分钱）
3. API 采用 OpenAI 兼容格式，迁移成本低
4. 支持长上下文（对话历史 + 用户记忆注入）

**缺陷**：无 embedding API，如需向量化需另接模型。

---

### 图片生成模型：字节豆包（火山引擎）

**决定**：使用字节跳动豆包图像生成（火山引擎，volcengine.com），替代 OpenAI。

**理由**：
1. 国内 IP 可直连，无需中转
2. 备案适配，商用合规
3. 价格平价（约 ¥0.01–0.05/张）
4. 教案示意图质量足够

**取舍**：风格灵活性可能低于 DALL-E，但教案辅图场景需求不高。

---

### 知识库：框架提炼 + （可选）向量 RAG

**决定**：MVP 阶段只做框架提炼，暂不做全文向量检索。

**理由**：
1. 版权风险最小化（不入库、不检索、不输出原文）
2. 成本零（无需向量库、无需 embedding 调用）
3. 效果足够（提炼出的质量标准和模板已是 80% 的价值）
4. 开发时间短（可同步推进，不阻塞原型）

**框架提炼产出**：
- 教案质量标准清单（科学性、安全性、适龄性、可执行性等维度）
- 通用教案模板（活动名、年龄班、目标、材料、流程、评估）
- 引导设计树（grill-me 风格，2–3 轮提问）
- 系统提示词初稿

**后续优化**：如老师反馈需要"查看类似案例"，再上向量库。

---

### 用户记忆实现：关系数据库 + 内存注入

**决定**：使用 PostgreSQL 或 MySQL 存储用户档案、对话历史、记忆条目；每次对话开始时把全量记忆注入系统提示词。

**理由**：
1. MVP 阶段记忆条目量小（几十条/用户），无需向量检索
2. 简化逻辑，降低复杂度
3. 隐私友好（纯结构化存储，无向量泄露风险）

**记忆写入流程**：
- 教案完成后，后端额外调一次 DeepSeek
- 系统提示词要求输出 JSON（提取值得记忆的事实）
- 与已有记忆对比，新增或更新

**记忆读取流程**：
- 每次对话开始时，查询用户档案 + 全量记忆条目
- 按 `[档案] + [记忆 1] + [记忆 2] + ... + [用户输入]` 拼接
- 作为 system message 的一部分注入

**扩展预留**：如果记忆量超过 10000 条/用户，再加语义检索层。

---

### 部署架构

**决定**：个人开发阶段 → 腾讯云/阿里云轻量服务器（2核4G，年费几百元）+ 国内云数据库（RDS）+ 对象存储（COS/OSS 存图）。

**ICP 备案链路**：
1. 购买域名和服务器（同一家云服务商加速）
2. 云商后台提交 ICP 备案（个人主体，约 1–3 周）
3. 获得备案号后，小程序后台添加服务器域名

## 替代方案考虑

| 方案 | 优点 | 缺点 | 采纳？ |
|------|------|------|--------|
| 原生 APP (Flutter) | 性能最好、跨端灵活 | 个人主体上不了 iOS；安卓审核慢 | ✗ |
| OpenAI + 国产图片 | 文本能力最强 | IP 被墙，需中转；成本高 | ✗ |
| 全文向量 RAG | 老师可查阅原书案例 | 版权风险；成本高；开发复杂 | ✗ |
| Redis 缓存记忆 | 性能快 | 向量化成本、私密性差 | ✗ |
