# ADR 004: 名单从「一个园」扩到「两个地区」，并开放「不在名单之内」

## 状态

已采纳 (2026-09-21)。修改 ADR-002 与 `api-spec` 中关于**兑换码语义**的两处表述
（「你是这批人里的」→「你有资格进来」）。

## 背景

原来的身份模型是：

```
兑换码   →  证明「你是这批人里的」
从名单里选 →  证明「你是哪一个」（园所 → 班级 → 岗位）
手机号 + 密码  →  你下次怎么进得来
```

码是**一个园一个园**发的，而名单是**一个园一个园**录的。
`redemption_codes.kindergarten_id` 有值时叫「绑定码」，问「发了几个、兑了几个」靠它。

2026-09-21 用户要**扩大用户**：

> 提供一个比较大的白名单，2 个地区（北京，广州），10 个幼儿园（每个地区 5 个园），
> 每个幼儿园都有 10 个老师…… 下拉框下方始终有一个「不在名单之内」的选项

## 决策

**四条**：

1. **兑换码不限定园所、也不限定「这批人」。** 任意有效未使用的码，
   都能查到任何园的位置，也能走「不在名单之内」。
2. **白名单变成两级地区 + 三层**：省 → 市 → 园所 → 班/岗位/人（四级下拉）。
3. **「不在名单之内」是常驻入口**，不审核。她填姓名、园所名、省、市、园所类型，
   然后跟白名单老师一样设手机号 + 密码。
4. **完善信息（出生年份 / 最高学历 / 教龄 / 当前任教年级）送 10 教案 + 5 配图**，只能领一次。

## 🔴 一处必须说准的话：门还在，白名单扩了

用户原话：

> 「有码才能进」依旧真实，只不过不再限定于「这批人」，我希望扩展我的用户

所以：

- **没有码的人什么都做不了** —— 拉名单要码、激活要码，这道门没动
- 变的是**门后面的白名单**：从「某一个园的名单」扩到「两个地区的 100 人 + 任何自填的人」
- `CLAUDE.md` 里「兑换码证明你是这批人里的」这句**不再准确**，
  已改成「证明你有资格进来」

**不要**把它读成「码作废了」或者「谁都能进」—— 两句话差别很大，
而后者会让下一个维护者以为鉴权被拿掉了。

## 认下来的代价

### 1. 「发了几个、兑了几个」对自填的人不成立

码不再绑定批次之后，跟进依据只剩**白名单老师那一部分**（他们的位置有人认领）。
自填的人回答不了「这个园发了几张码」，因为他们从来没在名单上。

**用户 2026-09-21 明确知情。** 他不再需要按园所跟进，要的是**扩大用户**。

### 2. 白名单老师仍然按园所分组，自填的人分不了

- 白名单老师：地区从 `kindergartens.province/city` 带出来，**干净**
- 自填的人：地区从**下拉**里选（不是自由填），所以也是干净值

⚠️ **「用下拉不用自由填」这个决定是数据质量的生命线。**
自由填会脏成「北京 / 北京市 / 北京朝阳」，而研究上要按地区分组 ——
那种数据**分不了组，而且脏了之后补不回来**（她填完就跑了，没人会去回访纠正）。

所以地区在**服务端也要校验**（必须出现在 `kindergartens` 的 DISTINCT 里），
不只是前端给个下拉。前端那道挡不住 curl。

### 3. 冒领从「同事之间」扩到了「任何有码的人」

原来认过的代价是：

> 从列表里选是一个**表单字段，不是钥匙**。可以接受，因为**同事之间**冒领没有收益

**码不再绑定园所之后，「同事之间」这个前提不再成立** —— 拿到码的陌生人也能
滚动到任何一个园、任何一个待认领的位置，冒领一位还没激活的老师。

仍然接受，理由有两条：

- **收益很低**：她冒领到的只是一个「位置」（园所/班级/岗位），额度是码本身发的，
  冒领不会多拿一次额度
- **可查可改**：`teacher_roster.claimed_by` 记着是谁认领的，改回来是后台一个动作

⚠️ 但**这条的严重程度确实比原来高了**，因为暴露面从「一个园」变成「两个地区」。
真要收紧，正确的做法是**让码重新带上园所**（`kindergarten_id` 已经在表里了，
只是现在不拿它过滤）。**这次没做**，因为用户明确要的就是「任意码都有效」。

### 4. 「不在名单」的人没有班和岗位

`teacher_roster` 那一行 `class_name` / `position` / `age_group` 全是 NULL ——
她没提供，**而且不该编**。

后果：研究上「这位老师在哪个岗位」这一维对自填的人缺失。
用 `teachers.entry_source`（`'roster'` / `'self'`）能把这个群体单独分出来。

## 为什么方向不是「新建一套身份」

考虑过：既然白名单的形状变了（多了地区一层），是不是该重做一张表。

**没做**，理由：

- `kindergartens` 已经有 `province` / `city`，只差一个 `district` ——
  加一列比建一张 `regions` 表便宜得多。**10 个园 2 个地区，独立表是过度设计**
- `teacher_ref` 那三层身份（人 / 位置 / 账号）**跟地区无关**，不用动
- `teachers` 上**已经有** `education` / `teaching_years` / `professional_title` /
  `kindergarten_name` —— 018 迁移早就加了，一开始以为要新建 `teacher_profile` 表，
  查过才发现不用

**教训**：改 schema 之前先查库里有什么。这次差点白建一张表。

## 顺带修掉的一个真实缺口

`ownership`（园所类型）的白名单**原来散在三个文件**：

```
services/tasks.js                ['public', 'private']
routes/admin/kindergartens.js    ['public', 'private'] + 一份中文映射表
```

要加「普惠民办」这一档时，**改一处不够** —— 而漏掉的那处**不报错**，
只会让定向任务永远筛不到那些园所（`tasks.js` 拿它筛目标人群）。

现在只有 `services/roster.js` 的 `OWNERSHIPS` 一份，其余两处 import 它。
存储值同时从英文 `public`/`private` 改成中文三项，跟已有的
`EDUCATIONS` / `TITLES` / `AGE_GROUPS` 保持一致 —— 混着英文码的代价是
**每次导出研究数据都要再翻译一次**，而那种翻译迟早在某一版脚本里漏掉一个值。
